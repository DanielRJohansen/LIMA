# Core MD features GROMACS has and LIMA lacks (status checked 2026-10-13)
- **`[ constraints ]` sections:** not read yet. constraints = h-bonds and `[ settles ]` are handled (see Constraints below), but topologies that list their constraints explicitly lose them.
- **Thermostat compatibility:** Salad uses `tcoupl = v-rescale`, `tau_t = 0.1`, `ref_t = 300`. LIMA’s thermostat behavior must be compared with and, if needed, made compatible with GROMACS v-rescale. This matters because thermostat behavior depends on the kinetic-energy convention used by the integrator.
- **MDP validation:** Explicitly validate/reject unsupported settings instead of silently ignoring them, including `rvdw`, PME grid settings, neighbor-list behavior, constraints, thermostat parameters, output cadence, and seeds.
- **Regression coverage:** Add a small AMBER99SB/TIP3P constrained-water fixture with tests for topology loading, constraint preservation, short-run stability, and readable `.trr` output. Validate against GROMACS observables, not frame-by-frame coordinates.
## Constraints: done for constraints = h-bonds (2026-10-13): bonds to hydrogens, and 3-atom water made rigid via its H-H distance. Groups (<=4 atoms, <=3 constraints) are kept within one pcluster, and SuperclusterIntegrateConstrainedKernel solves them per pcluster with SHAKE/RATTLE (deterministic, one thread per pcluster). Constrained bonds stay in the bond lists (0 energy at the constrained length), so EM and MD can share a box. T4 in water: constraint error < 1e-5, energy conservation better than flexible at 2 fs. Left:
- LINCS / constraints = all-bonds: postponed, h-bonds covers the usual CHARMM/AMBER setups. Needs coupled constraints across pclusters, ie. across superclusters, so a separate deterministic solver.
- Position precision limits all constraints: positions are absolute float coordinates in the box, so a 0.1 nm bond holds only to ~6e-6 relative whatever the solver. SETTLE (water, done 2026-10-13, constrained integrate kernel 36 -> 15 us on T4 in water) assumes the water is exactly rigid before each step, so it re-snaps the rounding every step: T4 VC over 10k steps 1.50e-5 vs 1.33e-5 with SHAKE. Store positions relative to the supercluster (or cell), as GROMACS keeps coordinates local, to remove this, which would also help everything else.
- Hydrogen mass repartitioning, for 4-5 fs steps. With constraints = h-bonds, T4 (vacuum and water) already runs 2000 steps at 4 fs without it; check energy conservation there first.
- initial_temperature draws velocities with components along the constraints, which the first step removes, so the start is somewhat colder than asked.
- Not yet compared with a constrained GROMACS run (bond lengths, water RDF, energy drift).
## Restraints: position restraints are skipped (posre includes ignored in Topologyfile.cpp), so no restrained equilibration. Also missing: distance/dihedral/flat-bottom restraints and pulling (umbrella sampling, steered MD).

# Implicit solvent (idea, 2026-10-12)
- Upper bound on the speed gain: STMV without water (167k of 1.07M atoms, same 22 nm box) runs 216.6 vs 43.7 ns/day, ~5x. Not 6.4x, because the PME grid and per-cell work stay the same. GB adds a Born-radii pass and a GB pair term, so expect maybe 2-3x net (estimate, unmeasured). Large charged systems like STMV are the worst case for implicit solvent (ions, structural water, salt bridges).
- ML implicit solvents (state as of 2026-10): GB + GNN correction is the realistic route for an MD engine. Riniker group (ETH): a GNN predicts per-atom corrections to GB-Neck2, transferable across small molecules in water (Chem. Sci. 2024), 39 organic solvents (JACS 2025), code at github.com/rinikerlab/GNNImplicitSolvent; validated on small molecules/peptides, not large proteins. Protein-trained GNNs (Airas/Ding/Zhang, ISSNet) match explicit ensembles on their training proteins; transfer is open. Implicit-water ML potentials (TWIN, 2026 preprint) are about accuracy, not speed: classical explicit TIP3P is still up to 25x faster per step, tested only on ~1.3k-atom proteins, no long-range electrostatics.
- Possible plan: 1) plain GB-Neck2 in LIMA (Born radii from the supercluster neighbor lists, GB term in or beside NbNonlocalKernel), measure against the 5x dry bound and check stability/accuracy vs explicit (eg. T4). 2) Only if worthwhile, add the GNN per-atom correction (local neighborhoods, which the neighbor lists already provide); its inference cost on large systems is unmeasured anywhere we found.

## Measure whether the default 0.05 nm pair list buffer causes real energy drift, before doing anything about it. GROMACS' buffer estimate (verlet_buffer_tolerance, implemented, off by default) asks for ~0.11-0.12 nm at nstlist 20 and 2 fs, which makes STMV ~11% slower, and by that (conservative) estimate 0.05 nm drifts well beyond GROMACS' 0.005 kJ/mol/ps per atom. Run eg. T4 in water for a long time (100k+ steps) with the default buffer and with verlet_buffer_tolerance=0.005, and compare the energy drift. Only if 0.05 nm drifts noticeably is it worth pursuing.
- Tried 2026-10-13 and reverted: dynamic pruning as GROMACS on GPUs (outer list with the accurate buffer every nstlist steps, a prune kernel every few steps recomputing each QuarterEntry's ownQuarterMask against an inner radius). It does not pay off in LIMA: NbNonlocal costs the same at inner radius cutoff+0.013 as at cutoff+0.05 (2.25 ms on STMV), as nearly every 4x4 block has a pair within the cutoff itself, so pruning only removes the outer buffer's cost, while the prune kernel (0.75 ms, one lane per entry) and the larger search cost more: STMV 4.04 vs 3.84 ms/step at nstlist 20 / prune 4. Longer nstlist does not help, as the outer buffer grows fast (0.29 nm at 40, beyond the cutoff at 80). Only worth revisiting with a much cheaper prune kernel (eg. NB's 4 lanes per entry) and if the drift measurement shows a need.

# Performance ideas. These are not set in stone todo's, rather concepts that are interesting to explore to see if they give any speed. Some makes the most sense together
- Instead of Env having a thread dedicated to RunSimulation, Engine instead get's it's own thread, so when engine starts an mdrun it literally only steps & updates the renderpipelin/simstatus. Another benefit is that Engine would persist, meaning slightly lower latency for setup. It's import that Engine free's its memory when it has no work, such that we are hogging 10 GB VRAM, while env is just doing preprocessing.
- EmitQuarterEntriesKernel: now ~0.77 ms per STMV rebuild (was 1.37). The cost was the bonded-pair exclusions (~1 active lane, dependent global loads): own particle ids now in shared memory, query ids loaded once per quarter, one pass over each bonded set for all 4 query particles. Rejected: int4 reads of the set (slower). What's left is mostly writing ~300 MB of QuarterEntries; shrinking that means changing NB's entry format.
- FindNeighborsKernel: now ~2.7 ms per STMV rebuild (was 3.9). Done: own-particle vs candidate-sphere prefilter (196 -> 140 pair-tested candidates/SC, 90 become neighbors), branch-free pair test, __launch_bounds__(128, 8) for 64 regs. The kernel is issue-bound (~68% issue active), so latency tricks don't help: 2 candidates per warp iteration and a candidate-particles vs own-sphere filter were both slower. Left: cell enumeration (~74 cells/SC, ~7 of 32 lanes active) and the bonded check (~8%).
- nstlist vs list-buffer tuning: a bigger buffer and fewer rebuilds may be cheaper overall. Parameter/accuracy call for you.
- NB kernel flattened entries: known ~4% SIMT gain left over from densetasks.


# Kernel graphs (prototyped, see stash "Tried cuda graph..."): T4 -11%, STMV +2.5%. Recipe:
- Engine.cuh: `std::array<cudaGraphExec_t, 2> stepGraphs{}` (indexed by logData) + `void LaunchStepGraph(cudaGraph_t, bool logData)`. Destroy the execs in ~Engine.
- _deviceMaster: after the `MakeSuperClusterTasksGPU` check and before `ForkStreamsFromMainStream()`, if `!emvariant && nSuperclusters > 0 && snf_select.empty()` (EM syncs mid-step, SNF unchecked): `cudaStreamBeginCapture(cudaStreams[0], cudaStreamCaptureModeThreadLocal)`. ThreadLocal so the log-drain thread's CUDA calls don't break the capture.
- The existing fork/join events pull the side streams (PME, bonds) into the capture; cuFFT exec captures fine. After the integrate launch: `cudaStreamEndCapture(cudaStreams[0], &graph)` -> LaunchStepGraph.
- LaunchStepGraph: if an exec exists try `cudaGraphExecUpdate(exec, graph, &info)`; on failure (topology changed after a task rebuild) `cudaGetLastError()`, destroy and re-instantiate. Then `cudaGraphLaunch(exec, cudaStreams[0])`, `cudaGraphDestroy(graph)`. Capturing every step means changed args (step, buffer pointers after Expand, live edits) need no tracking; ~10 us host/step, only ~4 re-instantiations per 2000 T4 steps.
- Measuring: nsys needs `--cuda-graph-trace=node` to show graph kernels, but node tracing perturbs scheduling (STMV looked faster under nsys, was slower in wall-clock). Trust wall-clock A/B (`--t4 2000 1`, `--stmv 300`) of the same binary.
- Findings: launch overhead is not the issue (host runs 0.25-41 ms ahead). Graphs fix WDDM submit batching that idled T4 normal steps 24/90 us -> 54 us steps. STMV loses because NB, PME spreading and bonds truly overlap and slow NB, which already fills the GPU (CUDA_DEVICE_MAX_CONNECTIONS=1: graph == no graph). Reordering launches (NB before PME) without graphs changed nothing.
- Next: encode the order (NB waits for an event after PME's ChargeblockDistributeToGrid, bonds wait for NB) so STMV is neutral and T4 keeps most of the gain; or graphs only below a system size.
